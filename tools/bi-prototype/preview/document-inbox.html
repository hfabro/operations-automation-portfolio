Supported text format and review boundaries
Each file starts with SYN-INVOICE-TEXT/1 and contains one Entity, Supplier, Invoice, Currency, Revision, Invoice-Date and Net-Total field, followed by contiguous Line 1–20 entries using PO reference | quantity | unit price. Optional Memo and # comment lines are retained. Repeated fields are ambiguous even when they agree; missing values and unrecognized instructions go to review.
Exact-copy checks hash the unchanged UTF-8 bytes, including BOM and line endings. Business duplicates use the normalized company/supplier/invoice reference. Revision 2 must identify the original SHA-256 and preserve company, supplier, invoice, currency, date, PO lines and quantities. Only price/header-net corrections use this demonstration’s independent approval control.
Supported UBL XML profile
SYN-UBL-2.1-NET-1 admits original UBL 2.1 Invoice documents (type 380), explicit buyer and supplier PartyIdentification IDs, a civil issue date, one currency, equal net/tax-exclusive/tax-inclusive/payable header totals, and 1–20 whole-quantity EA lines. Each line supplies its full approved PO line key in OrderLineReference/LineID and an exact unit price with explicit BaseQuantity 1 EA. There is no inferred supplier, account, PO join, unit or currency conversion.
Nonzero tax, allowances/charges, prepayments, attachments, extensions, correction references, other units, external schema references, repeated required elements and unsupported instructions go to AP document review. Malformed XML, DTD/entity declarations and foreign element namespaces are rejected by the profile. XML does not enter the text-format supplier-revision approval path. This is a bounded adapter, not full XSD, Peppol or EN 16931 validation.
The field definitions and namespaces follow the OASIS UBL 2.1 specification. All example business records are fictional. Loading either example batch replaces only this temporary inbox; download evidence first to retain current decisions.
How the demo is built
HTML, CSS and JavaScript provide the view. Browser Web Crypto computes SHA-256; bounded adapters extract actual fields with text-line references or namespace-aware XML paths. XML is parsed as an inert document with the browser’s native DOMParser; only admitted elements and attributes enter the existing normalized invoice model. The existing purchasing and multi-line invoice rule modules replay either the independent guided baseline or an explicitly captured saved purchasing checkpoint. Guided mode retains correction proposals and decisions. Captured mode previews original invoices, includes existing invoices in matching, and separates new hypothetical documents from effects on existing holds. Exact saved-value and canonical checkpoint fingerprints keep source ownership inspectable; changes invalidate the preview before evidence download. Evidence downloads include original text, hashes, field lineage and replayable checkpoints. No service or external upload is required.
This is not general invoice understanding, PDF/image/email OCR, a native Power BI report, a live ERP connector or a production access-control system. Extraction remains temporary and read-only. Explicit AP staging appends reviewed original invoices to the still-owned purchasing journal, with fingerprint receipts in unchanged import commands. Those receipts survive journal reload/export; the original bytes remain in the inbox evidence download. Reattaching a source verifies its hash and original normalized fields. No action joins the separate 90-day BI cohort. Source capture times and intake order are evidence only, not invoice aging or measured efficiency.
