# Business intelligence report for the simulated showcase

`preview/business-report.html` is a functioning browser BI presentation over the same validated purchasing journal used by the connected workflow. All company records and outcomes are simulated. The separate historical public-data analysis retains its own source/attribution and is not combined into this fictional company's totals.

## What the visitor can do

- Compare three checkpoints produced by real command replay: exception detected, supplier correction approved, and settled. Choosing a checkpoint changes the analytical view, not the visitor's workflow journal.
- Filter by cost center, account, and project. Group dollar allocations by any of those dimensions; select a bar to apply its facet.
- Select commitment, posted-invoice, unpaid or paid measures and inspect the PO-line/cost-center source rows behind the amount.
- Drill through to request/policy lineage, invoice versions and evaluation history.
- Review current exception types and distinct document counts. One document can have more than one reason; counts across reasons/cost centers are not added as separate invoices.
- Read the visitor's own fictional workflow journal, refresh it, or inspect a validated checkpoint file. An empty journal produces empty data, not substituted examples. Failed imports preserve the current report.
- Explicitly open a report checkpoint in the workflow. Replacement requires confirmation when it would replace a different saved journal. Analytical browsing alone does not update that journal.
- Download the complete inspectable JSON model/source checkpoint, or the filtered selected-measure CSV evidence. Formula-like text is escaped for spreadsheet-safe CSV display; integer monetary values remain exact.

## Reconciled example

| Checkpoint | Open PO commitment | Posted invoices | Unpaid | Paid | Unposted invoice-line value |
| --- | ---: | ---: | ---: | ---: | ---: |
| Exceptions detected | $3,750 | $0 | $0 | $0 | $3,850 |
| Correction approved, not posted | $3,750 | $0 | $0 | $0 | $3,750 |
| Settled | $0 | $3,750 | $0 | $3,750 | $0 |

The first checkpoint contains one invoice header, two invoice lines, and two blocking reason types. The pending price variance is $100, not savings. The reviewed revision removes that discrepancy but does not itself create a posting. Settled allocations are Facilities $3,000 / Production $750; equipment $2,500 / repairs $1,250. The Facilities equipment slice is $1,750. Filters and grouping preserve these totals without repeating the $3,750 header on each line.

Unsupported invoice currencies remain visible as held documents but are excluded from USD monetary measures. No exchange rate or implied conversion is invented. Calculated unposted line amounts are distinct from declared invoice-header amounts, which may themselves be on hold for reconciliation.

## Model contract

The projection is read-only. It validates the source journal and preserves its serialized commands/policy snapshot, enabling record-to-report replay.

| Table / collection | Grain and use |
| --- | --- |
| `costRows` | One approved PO line × cost-center distribution in one journal snapshot. Additive stage measures in USD cents. |
| `documents` | One invoice header, with supplier reference, currency, status, versions and evaluation history. Header net is document context, not an additive cost-center measure. |
| `invoiceAllocations` | One invoice document line × PO cost distribution. Its invoice currency and PO-basis currency are separate. Active unposted USD amounts support pending-value/variance measures. |
| `exceptions` | One currently held document × reason type. Current reason counts can overlap. |
| `exceptionHistory` | One document evaluation revision. These are evaluations, not necessarily separate newly created exceptions. |
| `audit` | One source-journal action, with explicitly simulated timestamps. |
| `dimensions` | Distinct cost centers, accounts, projects and PO-line lineage. |
| `sourceCheckpoint` | The validated original command journal for reproducibility, not another fact table to sum. |

For a native analytical model, relate dimensions to appropriate facts by declared keys. Use distinct document IDs in the invoice-allocation context for document counts under cost filters. Do not directly join and sum all receipt/invoice/payment child facts or repeat invoice headers. A document touching the selected cost slice can have review issues on another line; the report explicitly describes those reasons at whole-document scope.

Identifiers are unique within the exported journal. Assign a separate snapshot/dataset namespace before pooling multiple exports; do not sum full-state checkpoint balances across time as though they were transaction movements. `meta.journalRevision`, policy version and simulated as-of accompany every export. Native report authoring files are optional presentation artifacts; this page is accurately labeled browser BI, not an embedded Power BI report.

## Measures

Definitions live with the pure calculation module and are shown in the report. Ordered value, commitment and receipt proxy use the PO basis. Posted net invoices, unpaid and paid amounts use invoice/settlement allocations. Received-not-invoiced is within open commitment. Posted invoices equal unpaid plus paid. These stages must not be summed into a claimed total spend.

Coding coverage is shown as governed PO lines out of lines in the selection, not a business-wide automation-success percentage. No real savings, performance benchmark, actual processing duration or live-system claim is made. Simulated timestamps identify scenario order rather than operational throughput.

## Saved-journal handoffs

Explicit `?source=current` links open the validated saved journal; the paid overview card also selects the paid measure. Invalid saved storage on this direct entry hides unavailable financial figures, disables workflow replacement and provides a recovery destination. A guided example is shown only after the visitor explicitly chooses it. Normal navigation, refresh and failed-import preservation retain their established behavior.
