    Lifecycle controls
    • The requirement master and each occurrence have separate identities.
    • Completion requires an owner and evidence.
    • An exception requires an owner and explanatory notes.
    • Exceptions create a synthetic follow-up action and reminder event.
    • Historical occurrence records remain unchanged if the master changes later.

    Architecture behind recurring governance

    One requirement can generate many historically true records.

    The system separates stable rules from scheduled execution so ownership, due dates, evidence, and exceptions can change without destroying history.

    01 / master

    Stable requirement

    Defines cadence, evidence expectations, category, and default ownership.

    02 / occurrence

    Unique execution

    Each generated task has its own due date, owner, status, and completion record.

    03 / evidence

    Audit-ready record

    Completion and exceptions preserve the evidence and explanation valid at that moment.

    04 / visibility

    Management control

    Queue and reporting views derive from governed records rather than disconnected reminders.
