Operational analytics case study

Forklift Telemetry & Energy Analytics

REST API telemetry from five lithium-powered forklifts was modeled alongside 30-minute utility interval data to support questions about utilization, charging behavior, energy allocation, demand exposure, and operating trends.

Operational problem

Separate data sources hid the operating story.

Equipment telemetry and facility electrical data existed in different systems, making it difficult to understand utilization, charging sessions, state of charge, energy use, peak-demand exposure, and opportunities to shift activity.

Constraint

Different grains and clocks

Machine events and state samples do not arrive in the same structure or frequency as fixed utility intervals. Direct comparison without transformation would create misleading conclusions.

Approach

Model events before visualizing

API data was ingested and transformed into governed asset, timestamp, state, session, and measure structures, then aligned with facility intervals in a Power BI semantic model.

Fleet questionsUse, idle, charge, and state of charge
Energy questionsLoad windows, demand exposure, allocation

Architecture

Preserve grain, then relate context.

REST API + JSONAsset telemetry and time-stamped observations
Power QueryIngestion, normalization, typing, and transformation
Governed modelAssets, time, states, events, sessions, measures
Power BI + DAXSemantic measures and analytical context
Decision viewsFleet, charging, energy, demand, cost, trends
Parallel input

Utility interval data

Thirty-minute facility demand and consumption intervals enter the model independently and are related through a governed time dimension rather than forced into the telemetry table.

Interpretation control

Correlation is not automatic causation

Facility load includes more than material-handling equipment. Analytical views must distinguish measured values, modeled allocations, assumptions, and possible explanations.

Controls & failure modes

Analytics need operational controls too.

Data controls

Trust the inputs

  • Stable asset identities across API records
  • Consistent time zone and timestamp handling
  • Typed and validated values
  • Duplicate and missing record checks
  • Refresh and source-boundary visibility
Interpretation controls

Bound the conclusion

  • Separate measured, derived, and assumed values
  • Use a consistent time grain for comparisons
  • Flag incomplete charging sessions
  • Preserve fleet and asset-level views
  • Validate findings with operating context

Outcome

Data organized around decisions.

The architecture supports analysis of state of charge, charging sessions, active use, equipment utilization, charging windows, demand exposure, off-peak opportunities, energy allocation, and operating trends.

Energy result boundary

A separate energy-efficiency effort produced utility-verified annual savings of approximately 79,802 kWh and $9,802. Those verified savings demonstrate energy-management experience; they are not attributed entirely to the forklift telemetry application.

What I learned

The semantic model carries the judgment.

  1. Time alignment and grain are architecture decisions, not chart-formatting details.
  2. Operational definitions—active, idle, charging, session, peak—must be explicit before measures become trustworthy.
  3. The best analytical view makes uncertainty and attribution boundaries visible instead of hiding them behind a polished dashboard.
